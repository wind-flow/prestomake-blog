Markdown 블로그의 장점은 글을 단순한 텍스트 파일로 보관할 수 있다는 점입니다. 하지만 파일을 저장하는 것과 안전하게 발행하는 것은 다릅니다. 초안이 실수로 공개되거나 날짜 형식 때문에 빌드가 멈추지 않도록 단계별 확인 장치가 필요합니다.

## 초안과 공개 상태를 분리한다

글 파일의 메타데이터에 `draft` 값을 두고, 공개 빌드에서는 초안을 제외합니다. 파일명을 임시 표시로 사용하는 방법보다 규칙을 코드로 검사하기 쉽습니다. 예약 발행을 쓴다면 서버와 작성자의 시간대도 명시합니다.

제목, 설명, 발행일, 태그는 모든 글에 필요한 최소 필드로 정합니다. 사이트 생성기의 스키마 검사를 사용하면 누락이나 잘못된 날짜를 빌드 전에 발견할 수 있습니다.

## 미리보기에서 보는 것

맞춤법만 확인하지 않습니다. 제목 단계가 H1 다음 H2, H3 순서인지, 코드와 표가 모바일에서 넘치지 않는지, 내부 링크가 실제 경로를 가리키는지 봅니다. 이미지에는 내용에 맞는 대체 텍스트를 작성합니다.

목차가 지나치게 길다면 글의 범위가 넓다는 신호일 수 있습니다. 하나의 글이 여러 검색 의도를 동시에 해결하려 하지 않는지 다시 확인합니다.

## 자동 검사와 사람이 볼 항목

자동 검사는 필수 필드, 깨진 링크, 포맷, 빌드 성공 여부를 잘 찾습니다. 반면 글의 결론이 근거와 맞는지, 설명 순서가 자연스러운지는 사람이 읽어야 합니다. 두 검사를 대체 관계로 보지 말고 역할을 나눕니다.

권장 흐름은 다음과 같습니다.

1. 초안 작성과 출처 기록
2. 로컬 미리보기
3. 포맷·링크·빌드 검사
4. 모바일과 실제 읽기 검수
5. 공개 배포
6. 공개 URL 재확인

## 수정 기록을 남기는 이유

오래된 글을 고칠 때 발행일만 새로 바꾸면 독자는 무엇이 달라졌는지 알기 어렵습니다. 수정일과 핵심 변경 이유를 남기면 정보의 현재성을 판단할 수 있습니다. Git 커밋에는 변경 목적을 적어 이전 상태로 돌아갈 수 있게 합니다.

자동화의 목표는 검수를 없애는 것이 아니라 반복 실수를 먼저 잡는 것입니다. 공개 후 확인까지 발행의 일부로 정의하면 Markdown의 단순함을 유지하면서도 신뢰도 높은 운영이 가능합니다.
